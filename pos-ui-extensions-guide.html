The Case for Building

Why POS UI Extensions?

Traditional embedded apps load as web views inside POS — 3-5 second load times, inconsistent UI, no offline support. POS UI Extensions change the equation entirely.

⚡
Performance

Native speed, always

Extensions render as native components with local caching. Instant load vs 3-5s for web views. At a register where every second counts, this matters.

🎨
Consistency

Automatic Polaris design

Extensions automatically adopt the Shopify POS design system. Staff doesn't need to learn a different UI — everything feels like it belongs.

📍
Integration

Deep workflow integration

34 extension targets put your functionality exactly where staff needs it — Smart Grid, Cart, Product Details, Customer Profile, Receipts, and more.

📱
Cross-Platform

iOS and Android, one build

Write once, runs identically on both platforms. Lower development cost, easier maintenance, no platform-specific bugs to chase down.

📶
Resilience

Designed for offline

Stores lose internet. Extensions that plan for it keep working. The Storage and Connectivity APIs let you build graceful offline fallbacks.

🔮
Future-Proof

The platform's direction

App Bridge (legacy embedded apps) is being deprecated. POS UI Extensions are where Shopify is investing — build here, not on legacy infrastructure.

How It Works

Architecture

Understanding the runtime model is essential for making good decisions about offline behavior, bundle size, and API usage.

Runtime stack
POS App (iOS / Android)
  └── Extension Host (WebView)
        └── RemoteDOM Sandbox
              └── Your Extension (JS bundle from CDN)
                    └── POS APIs
                          (Cart, Customer, Session…)
Step 1 — Deploy

Your extension publishes as a JS bundle to Shopify CDN via shopify app deploy.

Step 2 — Discovery

POS registers installed extensions in its local DB at app startup.

Step 3 — Load

When a target activates (staff taps Smart Grid tile, opens cart, etc.), POS fetches and runs your bundle.

Step 4 — Render

RemoteDOM translates your components to native POS UI — no raw web view, real native rendering.

Security Model Extensions run in an isolated RemoteDOM sandbox. They have no access to the device filesystem, other apps, or any data outside the POS APIs explicitly exposed by Shopify.
Bundle Size Limit Each extension bundle is capped at 64KB compressed. The UI framework runtime consumes ~92% of that budget — leaving you ~5KB for your own code. Plan accordingly. See the Limitations section for workarounds.
POS Pro Required

POS UI Extensions require POS Pro. App Bridge (legacy embedded apps) works on Lite, but that's the surface being deprecated. If a merchant asks about extensions and they're on Lite, this is an upgrade conversation.

Extension Targets

Where your extension can live

Targets are the specific entry points in POS where your extension appears. There are 34 total, organized into three types.

🏠
Type 1

Tile Targets

Persistent tiles on the Smart Grid homepage. Staff sees them when they open POS. Best for: quick access, status indicators, workflow entry points.

pos.home.tile.render
📋
Type 2

Action Targets

Modals (full-screen overlay) or menu items in contextual screens. Staff triggers them on demand. Best for: multi-step workflows, forms, data entry.

pos.*.action.render
📌
Type 3

Block Targets

Inline content sections embedded inside native POS screens. Always visible when that screen is open. Best for: contextual metrics, instructions, read-only info.

pos.*.block.render
Critical Gotcha — Block targets are read-only Block extensions (inline content) cannot modify the cart, customer, or any POS data. They are display-only. If you need an action from a block, launch a modal (action target) from within it.

The Critical Gotcha

Offline support

Stores lose internet. Extensions that don't plan for it break at the worst possible moment — in front of a customer, mid-transaction. This is the #1 thing that separates good POS extensions from great ones.

Don't assume you have internet POS devices operate in retail environments where connectivity is intermittent. Any extension that makes uncached external API calls will fail when the network drops. Plan your offline strategy before you write a single line of code.
Works offline
  • ✓ UI rendering (always available)
  • ✓ Storage API (read/write local data)
  • ✓ Locale, Toast, Connectivity, Device
  • ✓ Scanner, Navigation, Action, PinPad
  • ✓ Cash Drawer
Does NOT work offline
  • ✗ External fetch() calls to your backend
  • ✗ Admin API / Direct API (GraphQL)
  • ✗ Cart, Customer, Order APIs
  • ✗ OAuth / app authentication
  • ✗ Gift card validation
Recommended pattern: cache + queue
offline-pattern.ts 
import { useConnectivity, useStorage } from '@shopify/ui-extensions-react/point-of-sale';

const { isConnected } = useConnectivity();
const storage = useStorage();

// When online: pre-cache critical data and flush queue
useEffect(() => {
  if (isConnected) {
    // 1. Refresh cache
    const data = await fetchCriticalData();
    await storage.set('cached_data', JSON.stringify(data));

    // 2. Flush pending operations
    const queue = JSON.parse(await storage.get('queued_ops') || '[]');
    if (queue.length > 0) {
      await processQueue(queue);
      await storage.set('queued_ops', '[]');
    }
  }
}, [isConnected]);

// When offline: use cached data, queue mutations
if (!isConnected) {
  const cached = JSON.parse(await storage.get('cached_data') || '{}');
  return <OfflineView data={cached} />;
}
Developer Guide

Build your first extension

From zero to a working Tile + Modal in under 10 minutes.

1 — Setup
Terminal 
# Create app
npm create @shopify/app@latest

# Generate POS extension
cd my-app
shopify app generate extension
# → Select: Point of Sale UI Extension

# Dev server (hot reload)
shopify app dev

# Deploy to production
shopify app deploy
Testing on device Log in to your dev store in the POS app (iOS or Android). Install your app. The extension appears automatically — no extra setup.
2 — Extension config
shopify.extension.toml 
api_version = "2026-07"

[[extensions]]
type = "pos_ui_extension"
name = "My POS Extension"
handle = "my-pos-extension"

[[extensions.targeting]]
target = "pos.home.tile.render"
module = "./src/Tile.tsx"

[[extensions.targeting]]
target = "pos.home.modal.render"
module = "./src/Modal.tsx"
3 — The Tile + Modal pattern (most common pair)
src/Tile.tsx — Smart Grid entry point 
import {
  reactExtension, Tile, useApi
} from '@shopify/ui-extensions-react/point-of-sale';

export default reactExtension(
  'pos.home.tile.render',
  () => {
    const api = useApi();

    return (
      <Tile
        title="My App"
        subtitle="Quick actions"
        onPress={() => api.action.presentModal()}
      />
    );
  }
);
src/Modal.tsx — Full-screen experience 
import {
  reactExtension, Screen, Navigator,
  Button, Text
} from '@shopify/ui-extensions-react/point-of-sale';

export default reactExtension(
  'pos.home.modal.render',
  () => {
    const api = useApi();

    return (
      <Navigator>
        <Screen name="Home" title="My App">
          <Text>Your extension here</Text>
          <Button
            onPress={() => api.action.dismissModal()}
          >
            Close
          </Button>
        </Screen>
      </Navigator>
    );
  }
);
4 — Debugging
Console

Dev Console in POS

iOS: Settings → Advanced → Enable Dev Console. Android: same path. Then shake device or 3-finger tap to open.

Chrome DevTools

Android remote debug

Navigate to chrome://inspect in Chrome desktop. Select the POS extension host from the device list.

Safari Web Inspector

iOS remote debug

Safari → Develop → [Your Device] → Select the Extensibility Host. Full DevTools available.

Known Limitations

What you can't do (and how to work around it)

Be honest about platform constraints with merchants and partners. These are real gaps with viable workarounds — knowing them makes you a better advisor.

Limitation 1

Bundle size capped at 64KB

The entire extension bundle must be under 64KB compressed. The UI framework runtime takes ~92% of that, leaving you ~5KB. This blocks complex multi-screen apps with rich local logic.

Workarounds
Terminal — analyze your bundle
# See what's eating your budget
npm run build -- --analyze
npx bundlephobia <package-name>  # check before installing

# Prefer small libs
# moment.js 67KB → date-fns 13KB
# lodash 71KB → lodash-es + tree shaking

# Externalise heavy logic to your backend
# Extension fetches processed data, doesn't compute it
Roadmap: shared chunks between extensions from the same app is under investigation.
Limitation 2

No native data visualization components

There are no chart or graph components. polaris-viz exists for web but is not available to POS UI Extensions due to RemoteDOM rendering constraints.

Workarounds
// Option A: ASCII art charts with Text
<Text>Sales:     ████████░░ 80%</Text>
<Text>Inventory: ██░░░░░░░░ 20%</Text>

// Option B: Generate charts server-side, return as image URL
const chartUrl = await fetch('/api/chart', {
  method: 'POST', body: JSON.stringify({ data: salesData })
});

// Option C: Unicode indicators
<Text>▲ +15% vs yesterday</Text>
Roadmap: not confirmed. No native chart components planned for POS UI Extensions currently.
Limitation 3

Cart validation: soft enforcement only

Extensions can show warnings but cannot block a sale. Staff can override everything. Shopify Functions (cart.validation.run) do NOT execute in POS — there's no hard validation capability.

Workarounds
// 1. Prominent warning (can't block, but can't be missed)
<Banner status="critical">
  ⚠️ Customer has reached purchase limit — manager approval required
</Banner>

// 2. Log overrides for audit trail
await fetch('/api/log-override', {
  method: 'POST',
  body: JSON.stringify({ staff_id: session.staffId, timestamp: Date.now() })
});
Roadmap: hard validation blocks are not on the near-term roadmap due to offline constraints.
Limitation 4

Block extensions cannot modify cart

Block targets (inline sections inside screens) are read-only. You cannot call Cart API, add items, or apply discounts from a block. Only action targets (modals) can mutate cart data.

Workaround — launch a modal from the block
// ❌ In a block extension — this will NOT work:
<Button onPress={() => cart.addLineItem(...)}>Add</Button>

// ✅ Correct pattern — launch modal from block, mutate from modal:
// Block:
<Button onPress={() => api.action.presentModal()}>Modify Cart</Button>

// Modal (pos.cart-details.action.render):
<Button onPress={async () => {
  await cart.addLineItem(...);
  api.action.dismissModal();
}}>Confirm</Button>
Limitation 5

No native custom fee primitive

There's no first-class way to add a named fee to the cart (e.g., "Service Fee: $5"). Workarounds either distort the product catalog or create messy line items in reports.

Common workarounds (all have trade-offs)
// Option A: Custom Sale (distorts reports — no SKU)
await cart.addLineItem({ title: 'Service Fee', price: '5.00', quantity: 1 });

// Option B: Dummy product in catalog (cleaner reports)
// → Create a "Fee" product, reference its variant ID
// → Contaminates catalog with non-real products

// ❌ Avoid: negative discount hacks — breaks reports entirely
Roadmap: custom fee primitive for POS Cart API has been logged as feedback. Not confirmed.
Technical FAQ

Hardest questions, direct answers

The questions that come up most often from developers building their first POS extension.

Can I reuse my Checkout Extension for POS? +
No — they are completely different surfaces. POS UI Extensions use pos.* targets and the POS UI Extensions APIs. Checkout Extensions use checkout.* targets and the Checkout UI Extensions APIs. The code is not portable between them.
How do I authenticate with my backend from an extension? +
Use api.session.getSessionToken() to get a short-lived Shopify session token, then pass it as a Bearer token to your backend. Verify it server-side using Shopify's Session Token verification endpoint. Never store credentials in the extension code itself. 
const token = await api.session.getSessionToken();
const res = await fetch('https://my-backend.com/api/data', {
  headers: { 'Authorization': `Bearer ${token}` }
});
Can I have multiple screens in my extension? +
Yes — use the Navigator + Screen pattern. This gives you a stack-based navigation inside your modal. 
<Navigator>
  <Screen name="Home" title="Main Screen">
    <Button onPress={() => navigator.push('Details')}>Go</Button>
  </Screen>
  <Screen name="Details" title="Detail">
    <Button onPress={() => navigator.pop()}>Back</Button>
  </Screen>
</Navigator>
How do I persist data between sessions? +
Use the Storage API. It's key-value local storage with limits: 100 entries max, 1MB per value, expires after 30 days of inactivity. 
// Write
await storage.set('prefs', JSON.stringify({ theme: 'dark' }));

// Read
const raw = await storage.get('prefs');
const data = JSON.parse(raw);
Can I use npm packages? +
Yes, but the 64KB bundle limit makes this tricky. Always check the package size with npx bundlephobia <pkg> before installing. Prefer smaller alternatives (date-fns over moment, lodash-es with tree shaking over full lodash). Packages that require native browser APIs or Node.js won't work in the RemoteDOM sandbox.
Can I share state between two extensions in the same app? +
Extensions are isolated singletons — there's no direct communication channel between them. The workaround is to use Storage API as a message bus: one extension writes state, the other polls for changes. 
// Extension A writes
await storage.set('shared', JSON.stringify({ data, ts: Date.now() }));

// Extension B polls
useEffect(() => {
  const iv = setInterval(async () => {
    const v = await storage.get('shared');
    if (v) setData(JSON.parse(v).data);
  }, 1000);
  return () => clearInterval(iv);
}, []);
Does POS UI Extensions require Shopify Plus? +
No. POS UI Extensions work on any plan that includes POS Pro. Plus is not required. POS Lite does not support UI Extensions — only App Bridge (legacy), which is being deprecated.
Can I access the device camera or barcode scanner? +
Yes — the Scanner API lets you read barcodes and QR codes. It works offline. 
import { useScanner } from '@shopify/ui-extensions-react/point-of-sale';

const scanner = useScanner();
const result = await scanner.scanBarcode();
console.log('Scanned:', result.barcode);
How do I handle network errors gracefully? +
Always wrap fetch calls in try-catch, show a Toast on failure, and fall back to cached Storage data. Never let an unhandled network error crash or freeze the extension UI. 
try {
  const data = await fetchData();
  await storage.set('cache', JSON.stringify(data));
  return data;
} catch (err) {
  api.toast.show(`Error: ${err.message}`, { isError: true });
  const cached = await storage.get('cache');
  return cached ? JSON.parse(cached) : null;
}
Can I modify the receipt? +
Yes, using the pos.purchase.receipt.render target. Your extension renders as a block appended to the receipt. For printing custom documents (invoices, etc.), use the Print API available since 2025-07.
Pre-Launch Checklist

Before you ship

Items that catch the most common launch issues before they reach merchants.

Build & Technical
  • Bundle size verified under 64KB (shopify app build → check output)
  • Tested on both iOS and Android — don't assume parity
  • Offline mode validated: kill wifi, test all critical flows
  • All async operations have error handling + Toast feedback
  • Loading states implemented for operations over ~300ms
  • API scopes configured correctly in Partner Dashboard
  • Bundle analyzed for unnecessary dependencies
  • Console cleared of debug console.log statements
Merchant Experience
  • Tested end-to-end with a real merchant workflow, not just isolated units
  • Extension shows meaningful state when first installed (not blank)
  • Error messages are human-readable, not stack traces
  • Offline fallback surfaces useful cached data, not an empty screen
  • Localization set up if merchants use multiple languages
  • Merchant-facing documentation updated before publish
  • Monitoring in place for error rates post-launch
